## The mitigation under review

- **Mitigation number:** 178
- **Mitigates failure mode:** #9 — *"Adversarial prompt bulking (increasing the number of
  prompts by multiplying them by the number of tactics)."*
- **Affected reliability dimension:** Comprehensiveness
- **Benchmark production stage:** (2) Prompt Generation
- **Risk reduction if adopted:** ~70.0% reduction in failure-mode likelihood; ~37.5%
  reduction in severity (context only — do not let these numbers change your verdict).
- **Example realization of the failure mode:** A benchmark designed to evaluate model
  robustness against jailbreaks creates 100 base adversarial prompts and then applies 10
  paraphrasing or obfuscation tactics to each, yielding 1,000 prompts. This gives the
  appearance of broad coverage, but the underlying semantic space is still narrow —
  centered on just 100 scenarios. A model that learns to defend against these specific
  base prompts or surface patterns scores highly while remaining vulnerable to novel or
  semantically different jailbreaks. A user assumes the model is robust and deploys it in
  a moderation tool, which is quickly circumvented by attacks not in the bloated set.

**Criterion question (answer this for the benchmark under review):**
> Are all prompts sourced from real users under normal circumstances?

## Mitigation-specific glossary (adds to the shared glossary)

- **Comprehensiveness:** The extent to which a benchmark fully represents or covers the
  range of inputs, use cases, or conditions relevant to the System Under Test (SUT)
  task, ensuring sufficient variability and representation. It asks, "will the relying
  user believe the benchmark covers something impacting their LLM decisions that is not
  covered?"
- **Adversarial Prompt Bulking:** The technique of increasing the number of prompts by
  multiplying them with various tactics (e.g., jailbreak templates) and root instances.
- **Tactics:** A transformation applied to a prompt to produce an altered prompt,
  typically for the purpose of jailbreaking a SUT.
- **Adversarial Users:** Individuals or entities that intentionally interact with an AI
  system in ways designed to exploit its vulnerabilities or induce harmful behavior,
  typically using jailbreaks to bypass guard mechanisms and move out of the intended task
  distribution.

## What counts as evidence the mitigation is in place

The evidence indicates the developer would likely assert the mitigation is in place when
the documents show **all** of the following for the *currently published* benchmark.
Each id below is a `requirement` key in the output.

1. **`real_user_sourced`** — The prompts are documented as originating from real users
   (e.g., logged interactions, public forums, deployed-system traffic), not synthesized
   or multiplied from a small set of root prompts via tactics.
2. **`normal_circumstances`** — The prompts reflect normal/naturalistic usage rather than
   contrived adversarial bulking, so the prompt set's semantic diversity matches genuine
   user behavior.

**Strong positive signals:** a description of collecting prompts from real user
interactions, query logs, or public forums; provenance/attribution of prompts to genuine
usage; an explicit statement that prompts were not generated by applying tactics or
perturbations to root prompts; counts that reflect distinct scenarios rather than
multiplied variants.

**Negative / disqualifying signals:** prompts produced by multiplying root prompts by
tactics/jailbreak templates; large prompt counts traceable to a small base set; synthetic
or template-generated prompts presented as broad coverage; no provenance for the prompts
at all.
